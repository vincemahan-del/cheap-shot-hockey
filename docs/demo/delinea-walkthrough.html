The rotation, end to end live

One credential-driven login test in the mabl cloud, against production. First: everything in sync.

# baseline
mabl tests run-cloud --id $TEST --credentials-id $CRED --app-url $APP_URL --no-prompt

Now Delinea rotates the Shared System ID — and nobody tells mabl. What happens to the next run?

# rotation without a sync
./scripts/delinea/rotate-shared-id.sh --skip-sync
mabl tests run-cloud --id $TEST --credentials-id $CRED --app-url $APP_URL --no-prompt

And the same rotation with the hook in place:

# rotation with the sync hook
./scripts/delinea/rotate-shared-id.sh
mabl tests run-cloud --id $TEST --credentials-id $CRED --app-url $APP_URL --no-prompt

The plumbing — rotation through test execution

Hop 3, under the hood

What the script sends

PATCH https://api.mabl.com/credentials/{id}
Authorization: Basic key:<workspace-admin key>
Content-Type: application/json

{ "properties": {
    "username": "svc-role-qa@…",
    "password": "<new value>" } }

What mabl does with it

  1. Authorizes — the key needs credential-write permission; anything less is refused with a named 403.
  2. Encrypts & stores — in transit and at rest, extra credential-layer encryption, keys in Google Cloud KMS.
  3. Audits — records who changed it and when; If-Match concurrency supported.
  4. Seals — cloud-only: no read path afterward, for anyone.
  5. Delivers just-in-time — the next run resolves the value at start and keeps it out of logs.
safe = Delinea Secret Server · lock change = password rotation (RPC) · hook = Event Pipeline “Run script” task · slot = cloud-only mabl credential · robot = mabl tests
